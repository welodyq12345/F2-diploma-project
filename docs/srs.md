# Software Requirements Specification (SRS) — FinJar

Специфікацію сформовано відповідно до структури ISO/IEC/IEEE 29148:2018.

## 1. System Context (Контекст системи)

FinJar — клієнт-серверна вебплатформа обліку коштів у гетерогенних гаманцях з мультивалютним реєстром подвійного запису, автоматизованим розподілом доходу за процентними правилами та LLM-асистентом.

**Межі системи (Scope).** До системи належать: клієнтський застосунок Next.js, REST API на Django REST Framework, Celery-воркери, PostgreSQL, Redis, RabbitMQ. Поза межами системи: банківські системи, постачальник курсів валют, LLM Provider, сервіс електронної пошти, платіжний провайдер підписок.

**Зовнішні взаємодії.**

| Зовнішній учасник | Тип | Взаємодія |
|---|---|---|
| Individual User, Family Member, Business Accountant | Актор | Вебклієнт (HTTPS) |
| FX Rates Provider | Зовнішня система | REST / HTTPS, отримання курсів за розкладом |
| Bank Webhook Source | Зовнішня система | HTTPS webhook з HMAC-підписом |
| LLM Provider | Зовнішня система | REST / HTTPS, tool calling |
| Email Service | Зовнішня система | SMTP / HTTPS API |
| Payment Provider | Зовнішня система | REST / HTTPS, webhook подій підписки |

## 2. Functional Requirements (Функціональні вимоги)

| ID | Вимога |
|---|---|
| <a id="srs-fun-01"></a>SRS-FUN-01 | Система повинна реєструвати користувача та автентифікувати його за email і паролем з видачею пари JWT (access / refresh). |
| <a id="srs-fun-02"></a>SRS-FUN-02 | Система повинна створювати гаманець одного з типів `bank_card`, `credit_card`, `crypto_wallet`, `cash` з валютою за ISO 4217. |
| <a id="srs-fun-03"></a>SRS-FUN-03 | Система повинна зберігати для гаманця типу `credit_card` кредитний ліміт і поточну заборгованість. |
| <a id="srs-fun-04"></a>SRS-FUN-04 | Система повинна реєструвати кожну транзакцію щонайменше двома проводками з рівною сумою дебету та кредиту в межах однієї ACID-транзакції. |
| <a id="srs-fun-05"></a>SRS-FUN-05 | Система повинна фіксувати в кожній проводці мультивалютної операції курс валют і суму в базовій валюті користувача. |
| <a id="srs-fun-06"></a>SRS-FUN-06 | Система повинна оновлювати курси валют від FX Rates Provider кожні 60 хвилин і кешувати їх у Redis. |
| <a id="srs-fun-07"></a>SRS-FUN-07 | Система повинна зберігати процентні правила розподілу доходу, сума часток яких дорівнює 100%. |
| <a id="srs-fun-08"></a>SRS-FUN-08 | Система повинна застосовувати активні правила розподілу до вхідного платежу асинхронно та не більше одного разу для кожної події надходження. |
| <a id="srs-fun-09"></a>SRS-FUN-09 | Система повинна виконувати зняття коштів з баночки з обов'язковим коментарем довжиною від 1 до 500 символів. |
| <a id="srs-fun-10"></a>SRS-FUN-10 | Система повинна записувати кожну зміну фінансових даних в append-only журнал аудиту. |
| <a id="srs-fun-11"></a>SRS-FUN-11 | Система повинна надавати ролі `owner`, `member`, `viewer` у спільному бюджеті тарифу Pro та перевіряти їх для кожного запиту. |
| <a id="srs-fun-12"></a>SRS-FUN-12 | Система повинна обмежувати доступ до функцій відповідно до тарифу Free, Pro або Business. |
| <a id="srs-fun-13"></a>SRS-FUN-13 | Система повинна відповідати на запит користувача природною мовою, використовуючи лише read-only інструменти API в межах даних поточного користувача. |
| <a id="srs-fun-14"></a>SRS-FUN-14 | Система повинна генерувати звіт витрат за період у форматах CSV і PDF у фоновому режимі. |

## 3. Non-Functional Requirements (Нефункціональні вимоги)

| ID | Категорія | Вимога |
|---|---|---|
| <a id="srs-nfr-perf-01"></a>SRS-NFR-PERF-01 | Продуктивність | Час відгуку REST API на читання повинен становити p95 ≤ 200 мс при навантаженні 300 RPS. |
| <a id="srs-nfr-perf-02"></a>SRS-NFR-PERF-02 | Продуктивність | Час відгуку на створення транзакції повинен становити p95 ≤ 350 мс при 100 RPS. |
| <a id="srs-nfr-perf-03"></a>SRS-NFR-PERF-03 | Продуктивність | Розподіл доходу повинен завершуватися ≤ 5 с (p95) від фіксації надходження. |
| <a id="srs-nfr-perf-04"></a>SRS-NFR-PERF-04 | Продуктивність | Відповідь LLM-асистента повинна надходити за p95 ≤ 8 с; запит повинен перериватися через 20 с. |
| <a id="srs-nfr-sec-01"></a>SRS-NFR-SEC-01 | Безпека | Access-токен JWT повинен діяти 15 хв, refresh-токен — 7 діб з ротацією та відкликанням. |
| <a id="srs-nfr-sec-02"></a>SRS-NFR-SEC-02 | Безпека | Паролі повинні зберігатися з хешуванням Argon2id; трафік повинен передаватися через TLS 1.2+. |
| <a id="srs-nfr-sec-03"></a>SRS-NFR-SEC-03 | Безпека | API повинен обмежувати частоту запитів до 100 запитів/хв на користувача та 10 спроб входу/хв на IP. |
| <a id="srs-nfr-sec-04"></a>SRS-NFR-SEC-04 | Безпека | Webhook-запити повинні перевірятися за HMAC-SHA256 підписом. |
| <a id="srs-nfr-sec-05"></a>SRS-NFR-SEC-05 | Комплаєнс | Система повинна надавати експорт і видалення персональних даних користувача (GDPR, ст. 17, 20) протягом 30 діб. |
| <a id="srs-nfr-rel-01"></a>SRS-NFR-REL-01 | Надійність | Реєстр не повинен містити транзакцій з розбіжністю суми дебету та кредиту. |
| <a id="srs-nfr-rel-02"></a>SRS-NFR-REL-02 | Надійність | Події повинні доставлятися за схемою at-least-once через Transactional Outbox; повторна обробка не повинна змінювати стан. |
| <a id="srs-nfr-rel-03"></a>SRS-NFR-REL-03 | Надійність | Доступність повинна становити ≥ 99.5% на місяць; RPO ≤ 24 год, RTO ≤ 2 год. |
| <a id="srs-nfr-ops-01"></a>SRS-NFR-OPS-01 | Експлуатація | Усі компоненти повинні розгортатися як Docker-контейнери; API повинен бути stateless. |
| <a id="srs-nfr-obs-01"></a>SRS-NFR-OBS-01 | Спостережуваність | Кожен запит повинен мати trace ID (OpenTelemetry); метрики повинні збиратися Prometheus. |
| <a id="srs-nfr-qa-01"></a>SRS-NFR-QA-01 | Якість | Покриття коду тестами повинно становити ≥ 70%; SonarQube Quality Gate повинен проходити без критичних зауважень. |

## 4. Verification Criteria (Критерії верифікації)

| Вимога | Метод верифікації |
|---|---|
| SRS-FUN-01, SRS-NFR-SEC-01 | Інтеграційні тести pytest + DRF APIClient: видача, закінчення строку та ротація токенів. |
| SRS-FUN-04, SRS-NFR-REL-01 | Property-based тести (Hypothesis): для довільних операцій сума дебету дорівнює сумі кредиту; SQL-інваріант у CI. |
| SRS-FUN-05, SRS-FUN-06 | Модульні тести модуля `fx` з фіксованими курсами (freezegun, respx-моки FX API). |
| SRS-FUN-08, SRS-NFR-REL-02 | Інтеграційний тест у Docker Compose: подвійна публікація події в RabbitMQ створює один набір проводок розподілу. |
| SRS-FUN-11, SRS-FUN-12 | Матриця тестів доступу (ролі × ендпойнти) у pytest; очікувані коди 403. |
| SRS-NFR-PERF-01, SRS-NFR-PERF-02 | Навантажувальний тест k6 (сценарії constant-arrival-rate та spike); поріг `http_req_duration{p(95)}<200`. |
| SRS-NFR-PERF-03 | Метрика Prometheus `allocation_latency_seconds` (гістограма), перевірка p95 у Grafana. |
| SRS-NFR-SEC-02, SRS-NFR-SEC-04 | Статичний аналіз SonarQube та Bandit; сканування образів Trivy; тести валідації HMAC. |
| SRS-NFR-SEC-03 | Тест k6: перевищення ліміту повертає HTTP 429. |
| SRS-NFR-OBS-01 | Перевірка наявності trace ID у Jaeger для наскрізного запиту. |
| SRS-NFR-QA-01 | Звіт pytest-cov та Jest coverage у GitHub Actions; SonarQube Quality Gate. |

## 5. Glossary (Глосарій)

| Термін | Визначення |
|---|---|
| Double-entry ledger | Реєстр, у якому кожна операція відображається щонайменше двома проводками з рівною сумою дебету та кредиту. |
| Jar (баночка) | Бюджетна категорія, що є окремим обліковим сховищем коштів користувача. |
| Transactional Outbox | Патерн, за яким подія записується в таблицю Outbox у тій самій транзакції БД, що й зміна даних, і публікується в брокер окремим процесом. |
| Idempotent Consumer | Споживач подій, який відкидає повторно доставлені події за унікальним ключем без зміни стану. |
| JWT | JSON Web Token — підписаний токен для передачі ідентичності та прав користувача. |
| Latency (p95) | Значення часу відгуку, яке не перевищують 95% запитів. |
| Eventual Consistency | Модель консистентності, за якої репліки даних досягають однакового стану через певний проміжок часу. |

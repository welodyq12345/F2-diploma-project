# РОЗДІЛ 1. АНАЛІЗ ПРЕДМЕТНОЇ ОБЛАСТІ ТА ПОСТАНОВКА ЗАДАЧІ ДОСЛІДЖЕННЯ

## 1.2 Аналіз існуючих програмних рішень

Для аналізу обрано три програмні системи, що вирішують задачу обліку та розподілу персональних фінансів: Monobank (функціонал «Банки»), Wallet by BudgetBakers та YNAB (You Need A Budget). Аналіз виконано за публічною технічною документацією (опис відкритих API, інженерні публікації розробників, умови використання). Внутрішні архітектурні рішення, які не розкриваються розробниками, позначено відповідно.

### 1.2.1 Monobank (функціонал «Банки»)

**Архітектурний патерн.** Банківська система з мобільним клієнтом як основним каналом обслуговування. Функціонал «Банки» реалізовано всередині core banking системи: кошти банки є окремим субрахунком у межах валюти рахунку клієнта. Внутрішня декомпозиція сервісів публічно не розкривається.

**Протоколи взаємодії.** Публічний Open API (REST / HTTPS, JSON) з автентифікацією за персональним токеном `X-Token`; надсилання подій про транзакції через webhook (HTTP POST на URL клієнта). Запит виписки обмежено частотою 1 запит на 60 секунд та інтервалом до 31 доби.

**Стек даних та консистентність.** Облік ведеться в банківському реєстрі з транзакційною (ACID) консистентністю в межах банку. Через API доступні лише рахунки та банки самого Monobank; дані інших банків, криптогаманців і готівки не агрегуються.

**Технічні обмеження (Technical Bottlenecks).**

- Закритість екосистеми: облік обмежено рахунками одного банку, відсутня модель гетерогенних гаманців.
- Мультивалютність реалізовано як окремі валютні рахунки без консолідованого балансу в базовій валюті.
- Розподіл одного надходження на кілька банок за процентними правилами не є декларативним правилом користувача; поповнення виконується окремими операціями.
- Rate limit Open API (1 запит/60 с на виписку) унеможливлює синхронізацію в реальному часі через polling; потрібна обробка webhook.

### 1.2.2 Wallet by BudgetBakers

**Архітектурний патерн.** Клієнт-серверна система з мобільними клієнтами (Android, iOS) та вебклієнтом; синхронізація даних між пристроями через хмарний бекенд. Підключення банківських рахунків виконується через сторонніх агрегаторів відкритого банкінгу (open banking aggregators).

**Протоколи взаємодії.** REST / HTTPS між клієнтами та бекендом; інтеграція з банками — через API агрегаторів (PSD2 / Open Banking); імпорт виписок у форматах CSV, OFX, QIF. Публічний API для сторонніх розробників обмежений.

**Стек даних та консистентність.** Записи зберігаються локально на пристрої та синхронізуються з хмарою; багатопристроєвий режим працює за моделлю eventual consistency з розв'язанням конфліктів під час синхронізації. Серверні СУБД публічно не розкриваються.

**Технічні обмеження (Technical Bottlenecks).**

- Залежність від сторонніх агрегаторів: збої або зміна умов агрегатора спричиняють розриви синхронізації та дублювання транзакцій.
- Конвертація валют виконується за поточним курсом відображення; історичний курс на момент операції не є обов'язковою частиною запису.
- Відсутній механізм автоматичного процентного розподілу доходу між категоріями; бюджети є лімітами витрат, а не окремими сховищами коштів.
- Eventual consistency між пристроями спричиняє тимчасові розбіжності балансів у спільних рахунках.

### 1.2.3 YNAB (You Need A Budget)

**Архітектурний патерн.** Вебзастосунок та мобільні клієнти з централізованим бекендом; бюджетування за методом zero-based budgeting (кожна одиниця доходу отримує призначення — категорію).

**Протоколи взаємодії.** Публічний YNAB API (REST / HTTPS, JSON, OAuth 2.0 та Personal Access Token) з дельта-синхронізацією через параметр `server_knowledge`; ліміт 200 запитів на годину на токен.

**Стек даних та консистентність.** Бюджет є єдиним агрегатом із рахунками, категоріями та транзакціями; синхронізація клієнтів інкрементальна (дельта-запити). Серверні СУБД публічно не деталізуються.

**Технічні обмеження (Technical Bottlenecks).**

- Один бюджет має одну валюту: рахунки в інших валютах вимагають окремих бюджетів або ручної конвертації.
- Розподіл коштів між категоріями виконується вручну; правила автоматичного процентного розподілу надходжень відсутні.
- Ліміт 200 запитів/год обмежує інтеграційні сценарії та сторонню автоматизацію.
- Відсутня нативна підтримка криптовалютних гаманців.

### 1.2.5 Аналітичний висновок

Проведений аналіз встановив, що жодна з розглянутих систем не поєднує мультивалютний облік гетерогенних гаманців з автоматизованим процентним розподілом доходу. Monobank реалізує модель банок як субрахунків у межах закритої банківської екосистеми, що виключає агрегацію коштів інших банків, криптогаманців і готівки. YNAB обмежує бюджет однією валютою та передбачає ручний розподіл коштів, а Wallet by BudgetBakers залежить від сторонніх агрегаторів відкритого банкінгу та застосовує модель eventual consistency, що спричиняє тимчасові розбіжності балансів.

Обрана для FinJar архітектура усуває виявлені обмеження. Реєстр операцій за принципом подвійного запису з атомарними транзакціями PostgreSQL і типом `NUMERIC` забезпечує консистентність балансів кожного гаманця та баночки. Фіксація курсу валют у записі транзакції уможливлює коректний консолідований баланс у базовій валюті на будь-яку дату. Асинхронний розподіл доходу через Celery та RabbitMQ з патернами Transactional Outbox та Idempotent Consumer гарантує однократне застосування процентних правил за повторної доставки подій. Модульний моноліт на Django REST Framework зменшує операційну складність порівняно з мікросервісною декомпозицією за збереження чітких меж доменних модулів.

Із рішень аналогів запозичено механізм webhook-сповіщень про транзакції (Monobank) та дельта-синхронізацію клієнтів за маркером версії (YNAB). Свідомо уникнуто залежності від одного агрегатора даних та моделі однієї валюти на бюджет. Сформовані висновки визначають вимоги до проєктування архітектури системи, що розглядаються в Розділі 2.

## 1.4 Аналіз обраної предметної області (модель As-Is)

### 1.4.1 Загальна характеристика домену

Предметна область охоплює облік, конвертацію та планування персональних, сімейних і корпоративних фінансових потоків. Станом на 2026 рік домен визначають такі тенденції: поширення відкритого банкінгу (PSD2 / Open Banking API), зростання частки мультивалютних заощаджень і криптоактивів у персональних портфелях, перехід від ручного обліку до подієвої обробки банківських сповіщень (webhook) та інтеграція LLM-асистентів у фінансові застосунки для аналізу витрат природною мовою.

### 1.4.2 Ключові актори та сутності

Актори: `Individual User` (власник персонального бюджету), `Family Member` (учасник спільного бюджету тарифу Pro з роллю `owner`, `member` або `viewer`), `Business Accountant` (користувач тарифу Business), зовнішні системи — постачальник курсів валют (FX Rates Provider), банківський API (джерело webhook-подій), LLM Provider.

Сутності: `Account` (обліковий запис), `Wallet` (гаманець типу `bank_card`, `credit_card`, `crypto_wallet`, `cash` з валютою ISO 4217), `Transaction` та `LedgerEntry` (проводки подвійного запису), `Jar` (бюджетна категорія-сховище), `AllocationRule` (процентне правило розподілу), `FxRate` (курс валютної пари на дату), `Subscription` (тарифний план), `AuditEvent`.

### 1.4.3 Бізнес-процеси As-Is та вузькі місця

**Процес 1. Облік надходження в мультивалютному портфелі.** Користувач отримує дохід на картку в одній валюті та тримає частину коштів у готівці й криптогаманцях інших валют. Наявні засоби (підрозділ 1.3) вимагають ручного внесення операцій для небанківських сховищ і конвертують валюти за поточним курсом відображення. Вузькі місця: розбіжність залишків після ручного введення; некоректний консолідований баланс через відсутність історичного курсу в записі операції; затримка обліку до моменту ручного введення.

**Процес 2. Розподіл доходу за бюджетними категоріями.** Після надходження заробітної плати користувач вручну переказує частки (наприклад, 30% — харчування, 10% — податки, 30% — заощадження, 30% — дозвілля) на окремі рахунки або банки. Вузькі місця: кількість ручних операцій лінійно зростає з кількістю категорій; помилки округлення розподілу; відсутність гарантії однократного застосування розподілу при повторному сповіщенні про надходження.

**Процес 3. Спільний сімейний та корпоративний бюджет.** Учасники ведуть облік у спільних таблицях або окремих застосунках з подальшим ручним зведенням. Вузькі місця: відсутність рольового контролю доступу; відсутність журналу аудиту змін; конфлікти одночасного редагування.

### 1.4.4 Регуляторні та індустріальні обмеження

Обробка персональних фінансових даних підпадає під вимоги GDPR та Закону України «Про захист персональних даних» (мінімізація даних, право на видалення, згода на обробку). Захист вебзастосунку регламентується OWASP ASVS 4.0 та OWASP Top 10. Подання сум регламентується ISO 4217 (коди валют) та вимогою точної десяткової арифметики. Інтеграція з банками через відкриті API обмежується лімітами частоти запитів провайдерів. Передача даних LLM-провайдеру вимагає знеособлення та передачі лише агрегованих показників.

## 1.5 Постановка задачі та формування вимог (модель To-Be)

### 1.5.1 Концептуальна модель To-Be

Надходження коштів на гаманець фіксується як транзакція в реєстрі подвійного запису в межах однієї ACID-транзакції PostgreSQL із фіксацією курсу валют на момент операції. У тій самій транзакції записується подія `IncomeReceived` у таблицю Outbox. Celery-воркер отримує подію через RabbitMQ, застосовує активні процентні правила користувача та створює проводки розподілу між баночками; ідемпотентність забезпечується ключем події. Консолідований баланс у базовій валюті обчислюється з проводок і зафіксованих курсів. Спільні бюджети контролюються RBAC, усі зміни реєструються в append-only журналі аудиту. LLM-асистент отримує доступ лише до read-only інструментів API в межах даних поточного користувача.

### 1.5.2 Функціональні вимоги (Core Features)

**Модуль `wallets`:**

- Створювати гаманці типів `bank_card`, `credit_card`, `crypto_wallet`, `cash` з валютою ISO 4217.
- Обліковувати кредитний ліміт і заборгованість для гаманців типу `credit_card`.

**Модуль `ledger`:**

- Реєструвати кожну транзакцію двома і більше збалансованими проводками (сума дебету дорівнює сумі кредиту).
- Фіксувати курс валют і суму в базовій валюті в кожній проводці мультивалютної операції.

**Модуль `fx`:**

- Отримувати курси валют від зовнішнього провайдера за розкладом Celery Beat і кешувати їх у Redis.

**Модуль `jars`:**

- Застосовувати процентні правила розподілу до вхідного платежу асинхронно та ідемпотентно.
- Виконувати зняття та переказ коштів між баночками й гаманцями з обов'язковим коментарем.

**Модуль `billing`:**

- Обмежувати функціональність відповідно до тарифу Free / Pro / Business та надавати ролі `owner`, `member`, `viewer` у спільному бюджеті.

**Модуль `assistant`:**

- Відповідати на запити природною мовою щодо балансів і витрат через read-only tool calling.

**Модуль `reports`:**

- Генерувати звіти витрат за категоріями, валютами та гаманцями у форматах CSV і PDF у фоновому режимі.

### 1.5.4 Постановка задачі

Таким чином, метою кваліфікаційної роботи є проєктування та розробка клієнт-серверної вебплатформи з архітектурою модульного моноліту на Django REST Framework та асинхронним контуром обробки подій на Celery і RabbitMQ для вирішення задачі консистентного мультивалютного обліку коштів у гетерогенних гаманцях з автоматизованим ідемпотентним розподілом доходу за процентними правилами, рольовим доступом до спільних бюджетів та LLM-асистентом з обмеженим read-only доступом до даних.

## Висновки до розділу 1

Аналіз ринку програмних засобів обліку фінансів встановив, що наявні рішення обмежені екосистемою одного банку (Monobank), однією валютою на бюджет (YNAB) або залежністю від сторонніх агрегаторів з моделлю eventual consistency (Wallet by BudgetBakers). Жодна з розглянутих систем не поєднує консистентний мультивалютний облік гетерогенних гаманців з автоматизованим процентним розподілом доходу, а розподіл коштів між бюджетними категоріями в усіх аналогах залишається ручною операцією.

Аналіз предметної області за моделлю As-Is локалізував вузькі місця: ручне введення операцій для небанківських сховищ, конвертацію за неактуальним курсом, лінійне зростання кількості ручних операцій під час розподілу доходу та відсутність рольового доступу і журналу аудиту у спільних бюджетах. Сформована модель To-Be усуває ці обмеження за рахунок реєстру подвійного запису в PostgreSQL, фіксації курсу в кожній проводці, асинхронного ідемпотентного розподілу через Celery, RabbitMQ і Transactional Outbox, а також RBAC і append-only аудиту.

Функціональні вимоги згруповано за сімома доменними модулями, нефункціональні вимоги задано вимірюваними метриками продуктивності (p95 ≤ 200 мс при 300 RPS), безпеки (JWT, Argon2, OWASP ASVS 4.0) та надійності (at-least-once доставка, SLA 99.5%). Проєктування архітектури системи, моделі даних і контрактів API, що реалізують зафіксовані вимоги, є предметом Розділу 2, а програмна реалізація та інструментальний аудит якості — предметом Розділу 3.
